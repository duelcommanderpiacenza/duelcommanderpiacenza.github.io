# Data model (Supabase, see `supabase/schema.sql`)

Part of the project notes split out of `CLAUDE.md` (read on demand, not loaded every session). Keep it in step with the code: update it in the same change. The access rules, migrations and local database are in CLAUDE.md.

| Table | Key fields | Notes |
|---|---|---|
| `leagues` | `name`, `is_open`, `is_topdeck` | **Planned (not built): `is_topdeck` → a generic `type` ('league' / 'topdeck' / 'online') for endstep online leagues — decisions in `ENDSTEP_PLAN.md`.** At most one open league and one open Topdeck series at a time (partial unique index). League score = each player's best (X−1) event scores, X = the league's *total* event count, open and closed (`computeLeaguePoints`'s `scheduledEvents`, from `Leagues.eventCount` → the `league_event_count` security-definer SQL function, since RLS hides a past-dated open event from anon) — so the live standings depend on the admin having created the league's future events ahead of time. Standings are always computed live; only the cached league badges need `syncAutoBadges`, fired on event open/close/delete and league create/open/close/delete (see the `player_badges_auto` row below) |
| `events` | `name` (nullable), `event_date`, `start_time` (optional), `league_id` (null = standalone), `rounds`, `is_open`, `results_url`, `decklists_url` (both optional, http(s)-only check constraints), `first_closed_at` (migration 022), `is_external`, `location` (migration 026), `venue` (migration 031) | An open/future event isn't "published" yet — only shown as a homepage preview. **External events** (`is_external`, migration 026): a standalone event played somewhere else, only announced on the Bacheca — set in the admin's Eventi standalone form ("Evento esterno" — only on a new event; its "Località", `location`, and its "Sito", `venue` — a shop or a club, migration 031; two external events may share a name if their date, Località or Sito differ — `events_unique_external`, nulls not distinct — while an ordinary standalone event's name stays unique, `events_unique_standalone_name`); no entries / matches / open-closed toggle (no Gestisci in admin), **open for good** (`events_external_open`; standalone only: `events_external_standalone`), so no "played" list anywhere picks it up; `events_public_read` lets visitors see it whatever its date. **`Events.list()` / `listUpcoming()` leave them out** (every page but the Bacheca; `notExternal` in db.js), the Bacheca reads them with `Events.listExternal()`, the admin with `listStandalone()` (two groups: "In programma", soonest first, then "Passati", latest first, each with its count; an external event's Località - Sito under its name, "Esterno" as its state); the send-decklist function refuses them. **Deleted the night after their day** (pg_cron job `delete-past-external-events`, 03:20 UTC, `event_date < current_date`; one without a date stays — migration 030), so they're only ever upcoming. On the Bacheca's timeline (js/home.js): only from today to 7 days ahead (`EXTERNAL_EVENTS_DAYS`), among ours by date, counted in its 4 upcoming; never a link (no page); the very next event of all, external or not, the red "next" one. **Its look: the colours of ours, a ticket's shape** (other colours were tried and found too loud — css/1 `.home-timeline .is-external`): a notch on each side, cut out of the card by a `mask` (transparent: the page shows through — half-circles painted in the page's colour showed as white discs), its edge a thin ring in the card's border colour (`--ring`, a background gradient), no shadow; its time at the bottom (`.league-tl-time`; ours keep the time on the league's line); the Località with a pin (`.league-tl-place`) in place of the league, then the Sito in red (`.league-tl-venue`: "Milano - Il Labirinto"; on the red "next" card white, the Località faded; cut with "…" when too long); no badge. The admin form's hint under the checkbox is empty unless it's locked ("Solo un evento nuovo può essere esterno."). `results_url` is the event's mtgtop8 top-decks link, `decklists_url` its Moxfield decklists link, both editable in admin even once closed, rendered by `js/results-link.js` — behind one "Liste" button (`nestedResultsMenu`) on the Bacheca's and league.html's rows and beside event.html's title. The menu lists each link with its logo (`moxfield.png`, `top8.png` — dark blue on transparent, only readable on white) |
| `event_entries` | `event_id`, `player_id`, `commander_id`, `partner_commander_id` (optional), `archetype`, `bonus_points`, `manual_rank` | One entry per player per event. **No `archetypes` table** — archetype is a fixed 5-value Postgres enum (aggro/control/combo/tempo/midrange) column directly on the entry. `bonus_points` (league-point adjustment) is edited inline in the admin *event leaderboard* ("Bonus lega" column, `matches-admin.js`, league events only, open events only), not in the Iscritti form |
| `matches` | `event_id`, `round`, `player1_id`, `player2_id` (nullable = bye), `player1_wins`/`draws`/`player2_wins` (game score, best-of-3: at most 2 wins each and 3 games in all — the admin form and `matches_score_valid`, migration 025), `is_drop` | Winrate everywhere on the site is **match-basis** — a 2-0 and a 2-1 match win both just count as one win (`wins / (wins+draws+losses)`), not the individual best-of-3 game score. The one deliberate exception is `js/leaderboard.js`'s MTG tournament tiebreakers (`buildTiebreakers`: Match/Game Win %, Opponents' Match/Game Win % — events tiebreak on OMW%→GW%→OGW%, league standings first on most 1st places, then most 2nd places, … across the league's events, then own MW%→GW%→OGW% over that league's matches only — `compareLeagueStandings`) — that's the official DCI/WPN tiebreak formula, a different, never-displayed calculation, not this site's own choice of how to show "winrate" |
| `commanders` | `name`, `color_identity`, `is_banned`, `is_new` (migration 027) | A "deck" elsewhere in the code = commander + optional partner combo, not just the commander alone. **Commander badges** (`commanderBadgesHtml({ banned, isNew })` in js/ui.js — the players' look: `badgeDiscHtml` in an `.icon-badge` with `badgeTooltipAttrs`' hover card; the site's own icons `icons/commanders/banned.svg` / `new.svg`, site-absolute paths so the admin's list works too): Comandanti's list (a partner pair: either one), commander.html's title, the admin's commander list ("Badge" column). **"Nuovo"** = `is_new`, a derived cache set only by `syncAutoBadges` (admin/js/badges-sync.js `syncNewCommanders`, so on every event open / close / delete): first appearance in a closed event (as commander or partner) within `NEW_COMMANDER_MONTHS` (1) before the **latest closed event** (not today: stable between events) and not within that long after the very first recorded event (before then it'd only mean "first recorded") |
| `players` | `name`, `handle`, `badge1_id`, `badge2_id`, `user_id` (the linked account — written only by the admin, see `player_claims`) | Two manually-assignable badge slots |
| `badges` | `name`, `description` (optional hover text of the badge icon next to player names, via `ui.js`'s `badgeTooltipAttrs`; empty = the name), `icon` (emoji) or `icon_url` (Storage), `auto_rule` (enum or null=manual), `priority` (still an integer in the DB, but the admin form only offers Alta=10 / Media=5 / Bassa=3 as a dropdown — `badges-admin.js`'s `priorityLevel` snaps any other value to the nearest level) | Auto-computed badges (league winner, top8 streak, etc.) are computed by `js/auto-badges.js` and cached into `player_badges_auto` by `admin/js/badges-sync.js` (triggers: see the `player_badges_auto` row below) — not live on every page view. Adding a new rule = its compute function + dispatch branch in `auto-badges.js`, `RULE_LABELS` + legend `<dl>` in admin, `RULE_TEXT` in `badges-page.js`, **and** the `badges_auto_rule_valid` check constraint in the DB (drop + re-add, see `schema.sql`) — without the SQL, saving a badge with the new rule fails |
| *(admin badge form)* | — | The emoji icon is picked with `admin/js/emoji-picker.js` — a keyboard-style picker (category tabs + scrollable grid of several hundred emoji, plus a "paste any emoji" field; first tab **"Custom"** = the site's own colour SVG icons in `icons/badges/`, listed by name in its `CUSTOM_ICONS` — no build step to read the folder, so a new icon = the file + its name there. Picking one sets the value to its site path, `/icons/badges/<name>.svg`, which the form saves as the badge's **`icon_url`** (icon null), so every page draws it like an uploaded picture with no rendering change; `isCustomIcon()` tells it apart from an uploaded one when editing, and `BadgeIcons.remove` ignores it, not being a storage URL) writing into the hidden `#badges-admin-icon`; `badges-admin.js` reads that field and calls the returned `setValue()` on edit/reset. Admin modules (incl. this picker) are only initialized after login (`app.js`'s `showAdmin`) |
| `player_badges_auto` | `player_id`, `badge_id` | Pure derived cache (no id/created_at) — fully replaced (delete-all + reinsert) by `admin/js/badges-sync.js`'s `syncAutoBadges()` (recomputes *every* rule for *every* player, closed events only), read by public pages via `js/db.js`'s `PlayerAutoBadges`. **Triggers** (admin only, the public site never recomputes): badge **save** (create or edit, unconditionally — `badges-admin.js`); event open-close toggle / delete (`events-admin.js`, `standalone-events-admin.js`, `app.js`'s event-detail toggle); league **create** (it auto-closes the previously open league of that kind) / open-close toggle / delete (`leagues-admin.js`). Deliberately **not** on event create: a new event starts open and empty, so no published result changes (its +1 to the league's X is picked up by the next trigger, e.g. closing it). Any new code path that closes/reopens an event or league must call it too. Always **fire-and-forget** (`.catch(console.error)`): the "Salvato." message appears before it finishes (several seconds). **Leaving or reloading the admin page meanwhile cuts it off** (the caches keep their old content — or, caught between a table's delete-all and insert-all, end up empty), so it shows its progress as an admin toast while it runs (`showStatus` → `showToast`, admin/js/toast.js: "Aggiornamento di badge e statistiche… non chiudere la pagina" → "aggiornati", red on failure, details in the console) and the browser asks before leaving (`beforeunload`). It **never runs twice at once**: a trigger during a run queues one more full run right after (two overlapping runs interleaved their delete-all/insert-all on the same tables, one failing on duplicate rows). The caches keep their previous content after a failure until the next trigger. Badge **delete** doesn't trigger it and needn't: `on delete cascade` drops that badge's cache rows. Manual badges (`players.badge1_id/badge2_id`) aren't part of this at all — saved directly on the player, visible immediately |
| `event_standings` | `event_id`, `player_id`, `position`, `points`, `wins`/`draws`/`losses` | Derived cache of every **closed** event's final standings (`computeEventLeaderboard`, same tiebreakers as event.html), fully replaced by the same `syncAutoBadges()` run (it rebuilds both caches, independently — one failing doesn't stop the other), so the first run after the table exists backfills every past event. Read by player.html's "Storico partite" (each event's final-position chip) via `EventStandings.listByPlayer` (a player's own few rows instead of every attended event's full entries + matches); any event missing from it (table not created yet, not yet rebuilt since closing, or open events seen logged in) falls back to computing it in the page. Public read gated to closed events, like `event_entries` |
| `player_progress` | `player_id` (pk), `events_played`, `matches_won`, `big_top8s`, `commanders`, `leagues_won` (text[] of league names) | The numbers behind the player card's cosmetics (`js/card-cosmetics.js`): a pure derived cache like `event_standings`, computed by `js/card-progress.js` over every closed event (a match won = a round won, a bye counts, a drop doesn't; top 8s only in events of 20+ entrants, `BIG_EVENT_MIN_PLAYERS`; commanders = commander + partner pairs, like the album; leagues won via `auto-badges.js`'s `closedLeagueWinners`) and fully replaced by the same `syncAutoBadges()` run (the closed results downloaded once, shared with `event_standings`). Read by account.html's and player.html's card (`PlayerProgress.get`); public read. Migration 011 |
| `decklist_submissions` | `player_id`, `event_id`, `attempt` (1 or 2 — the primary key, the three together), `user_id`, `sent_at` | Only *that* a player sent a decklist for an event (account.html's "Invia la tua decklist"), **never the list** — the list is emailed to the organisers by the **`send-decklist` Edge Function** (`supabase/functions/send-decklist/index.ts`, deployed from the Supabase dashboard, secrets `RESEND_API_KEY` + `DECKLIST_TO`; Resend's free plan without an own domain only delivers to the Resend account's address — the account is lamialistadeck@gmail.com's, the destination), which checks everything itself (signed in, not blocked, linked; the event upcoming, or closed with the player in it; not sent yet), claims attempt 1, else 2 (the key settles two sends at once; a third is refused, `already_sent`), sends — a second send's email says first that it replaces the first — and gives the row back if sending fails. Subject `<Event name> - <dd/mm/yyyy> - <Player name>`, Reply-To the account's email. Written only by the function (service role); read by the linked account and the admin; the admin deletes a row to allow another send. Migrations 008 (one per event) and 009 (two) |
| `user_settings` | `user_id` (PK), `theme` ('light' / 'dark' / 'system', null = never chosen since migration 024), `haptics` (boolean, null = never chosen — the footer's vibration switch, js/haptics-toggle.js, migration 024), `language` ('it' / 'en', null = never chosen — js/language.js, migration 033), `updated_at` | Settings remembered per account (migration 019): the theme picked from the footer button. Signed out the button just switches light ↔ dark (localStorage); signed in it opens a menu (Chiaro / Scuro / Segui il sistema, `js/theme.js`, `.theme-menu` above the button) and the choice is saved here (`UserSettings` in js/db.js) and applied on sign-in on any device (wins over the browser's own). **Read once per sign-in, not per page load** (theme, vibration and language alike — `firstReadSinceSignIn` / `forgetSynced` in js/theme.js, localStorage `settingsRead:<name>:<user id>`): after that the browser's copy is the setting (the buttons save both); signing out forgets the mark, so a choice made on another device arrives at the next sign-in. localStorage still drives first paint ("system" = no key). Its own table, not a `profiles` column: a profiles row means "has a player card" (saved by its owner, or the default one given at linking — migration 028). The button shows the choice as a line icon (sun / moon / screen), no emoji. **A tap that changes light ↔ dark** (the footer's button / menu, account.html's Impostazioni) **fades the old colours into the new ones** (`switchTheme` in js/theme.js — a 320ms cross-fade view transition of the whole screen, `html.is-theme-transition` clearing every other `view-transition-name` meanwhile, css/6 "Theme switch"; a circle growing from the tapped control was tried and dropped — too much); at once with reduced motion, without view transitions, or for a change not made by a tap (the device's own switch, the account's saved choice on sign-in). Private, own row only |
| `user_activity` | `user_id` (PK), `last_seen_at` | Each signed-in account's last visit to the site (migration 020), shown as the admin Utenti tab's "Ultimo accesso" (the date; falls back to `last_sign_in_at` when there's none). Written only by `touch_last_seen()` (security definer, the caller's own row), called by js/header-account.js on page load while signed in, at most every 10 minutes per browser (localStorage `lastSeen:<user id>`); no RLS policies — read only through `admin_list_users()` (which returns `last_seen_at` since 020). Admin pages don't count as visits |
| `announcements` | `title`, `body`, `expires_on` (optional date), `event_id` (migration 022) | Shown in the header's **"Novità" bell** on every public page (js/header-news.js, `Announcements.listActive`) up to and including its `expires_on` day. **Automatic ones**: closing an event for the first time adds "Risultati online: <event>" with its `event_id` (trigger `events_notify_first_close`, `events.first_closed_at` set once); the admin marks them "Automatico", not editable. Expired rows show in admin marked "scaduto" until the nightly `delete-expired-announcements` pg_cron job (03:15 UTC, see supabase/schema.sql) deletes them. `created_at` is kept only for newest-first ordering, never displayed |

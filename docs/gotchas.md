# Non-obvious gotchas (hit and fixed — avoid repeating)

Part of the project notes split out of `CLAUDE.md` (read on demand, not loaded every session). Keep it in step with the code: update it in the same change. The general rule they all come from is in CLAUDE.md.

1. **`overflow: hidden` on an element clips its own `::before`/`::after` too**, even ones meant to render outside its box (tooltips, dropdown shadows). If an element needs both truncation (`text-overflow: ellipsis`) *and* to host an absolutely-positioned popup/tooltip, put the truncation on an inner wrapper instead and keep the outer element unclipped.
2. **A scrolling container's `overflow-x: auto` forces `overflow-y` to also clip** (per the CSS overflow spec, whichever axis isn't explicitly set gets forced to `auto`/clipping too once the other is non-`visible`). A tooltip/popup anchored inside a horizontally-scrolling table (`.matchups-matrix-wrap`) cannot escape that clipping with CSS alone — it has to be a real element positioned via JS (`getBoundingClientRect`) and appended to `<body>`, outside the clipping ancestor. Use the shared `js/floating-tooltip.js` (`attachHoverTooltips(container, selector, textFor)` — the site's only tooltip: badges/banned icon/"Top 8" pill site-wide via `js/layout.js`, the Matchups headers and the Comandanti bar-chart labels; `fullTextIfTruncated` shows it only when a label is actually cut off; hover + keyboard focus; on touch, a tap on a badge inside a link card only shows its tooltip — `js/layout.js` cancels the link's click in the capture phase, mouse clicks still follow it).
3. **`mouseenter`/`mouseleave` don't bubble**, so event-delegation on a parent needs the capture phase (`addEventListener(type, fn, true)`). And if the hovered element has a child (e.g. a truncation `<span>` inside a `<th>`), capture-phase mouseenter/mouseleave fire *separately* for the child too as the cursor crosses that inner boundary — guard against re-triggering show/hide by tracking the currently-active target and checking `relatedTarget` on leave.
5. **Android's adaptive-icon system shrinks a non-`maskable` PWA icon defensively** (lots of padding) since it doesn't know how a launcher will crop it. A `purpose: "maskable"` icon variant with content filling ~70–80% of the canvas (this site uses 70%) against an opaque background fixes it — transparent backgrounds don't work for maskable icons, the OS crops the full square regardless.
6. **`beforeinstallprompt` is Chrome/Android-only** (and Edge / Samsung) — Safari/WebKit has never implemented it, on iPhone or iPad; the only install path on iOS is the manual Share → "Add to Home Screen". **The "Installa l'app" invitation** (`js/pwa-install.js`): once per visit (a session), ~1.5s after the content is in (`body.is-loading` gone), sliding up — the first 3 visits every time, then at most once every 7 days, never again after 3 "Non ora" (cancelling the browser's own install window counts as one) or once installed (`appinstalled` / accepted) or already open as the app; state in localStorage `pwaInstall` / `pwaInstallAdmin` (`{shows, dismissals, lastShown, installed}`). With `beforeinstallprompt`: a card (`.pwa-install-banner` — phones above the tab bar, computers bottom-right) whose "Installa" calls `prompt()`; iPhone / iPad: a bottom sheet (`.pwa-install-sheet`) with the Condividi → Aggiungi alla schermata Home steps; Android inside an app's own browser (Instagram, Facebook, WhatsApp…, UA sniffed): a sheet on opening it in Chrome and installing from the ⋮ menu; anything else: nothing.
7. Service worker (`sw.js`): **Scryfall's card images** (`cards.scryfall.io`, cache first, cache `scryfall-images-v1`, at most 300 — the oldest dropped; bump the version to empty it) — their addresses are versioned, so never stale; **the site's own files** network first, a copy as the offline fallback (`site-shell-v1`); **Supabase's data** (`supabase-data-v1`, at most 400): REST GETs **stale-while-revalidate** — the last visit's copy answers at once, the network's replaces it behind (waiting briefly for the network first was tried and dropped: pages shown as soon as possible come first), keyed per account (the token's `sub`, "anon") and Accept / Prefer header; a changed body → `postMessage("data-updated")` → `js/data-updates.js` redraws the page **quietly** (a full in-place reload flashed: splash, fade, animations again) if it's within 6s of arriving and untouched — `router.refresh({ keepScroll: true, quiet: true })`: a view transition whose update swaps `<main>`, mounts it and waits until it's whole (`whenDrawn`: splash gone, no `.sk` placeholder left outside it, the images in view decoded; ≤3s in all, `QUIET_MAX_WAIT`) while the browser keeps the old frame — the old screen's painted art and hero colour carried over first (`carryPaintedArt`: style / `data-url` / `is-loaded` / `has-hero-accent` of main, `.detail-hero-wrap`, `.profile-hero`, `.profile-hero-art`, `.pc-art`, so the painter skips the same art) —, then a 200ms cross-fade (`html.is-quiet-refresh`: no other transition names, every animation **and transition** jumped to its end — **except the phones' hero parallax** (`.profile-hero.is-parallax`, its art and content: scroll-driven, and its "end" is the hero pushed down by half and blurred) —, no count-up, `mix-blend-mode: plus-lighter` on the root's old/new — our `animation` drops the browser's own blend, and without it the cross-fade dipped to the bare background: a white flash over a dark hero (same for the theme switch); css/6 "Quiet redraw") — else (later, touched, or no view transitions / reduced motion) a "Dati aggiornati · Aggiorna" note at the top; network failure with a copy → "Offline · dati dell'ultimo accesso" for a moment. **Never stored** (`ALWAYS_FRESH`): the personal tables (profiles, user_settings, decklist_submissions, player_claims, user_activity, admins) and `announcements` (the header's bell isn't redrawn), nor `rpc`, non-GETs or the admin's requests (the client's URL under `/admin/`). Pull to refresh sends `"fresh-data"` → network first for that page for 5s. A new table read by a page is cached automatically — add it to `ALWAYS_FRESH` if it's personal or must never lag. The images are always fetched and stored as CORS responses (the hero art is also loaded with CORS for its colour; an opaque copy would fail that, and opaque entries count as MBs of quota each). Mentioned in privacy.html's "Cookie".
8. **A generic dark-mode override can win on specificity over a more specific context rule that resets a background to transparent**, even when that rule is more semantically "specific." The generic dark-mode "give this a faint card background" rules (css/6 near its top, the big `:root[data-theme="dark"] .card, .stat-tile, .pie-chart-wrap, .history-panel, …` list) are 3 classes; a narrower "this one shouldn't have its own background, it's nested inside another card" rule like `.dashboard-card-commanders .pie-chart-wrap { background: none; }` is usually only 2 — the generic rule wins regardless of source order, silently reintroducing a visible background the narrower rule was trying to remove. Hit several times with this exact shape (e.g. `.dashboard-card-commanders .pie-chart-wrap`, the admin's `.admin-tabs`) — worth checking for this pattern by default whenever a "make this transparent/none in context X" rule doesn't seem to be working in dark mode specifically. Fix is always the same: a compound selector combining `:root[data-theme="dark"]` (or `html[data-theme="dark"]`) with the narrower context class(es) in one selector, placed near the other dark-mode overrides, not just relying on cascade order.
9. **Wrapping already-class-gated CSS in a redundant `@media` condition means BOTH have to independently match, and they can disagree.** Gate touch styles on `html.nav-mobile` alone, never also on `(pointer: coarse)` / `(hover: none)` media: some browsers (Samsung Internet) misreport them, so the styling silently never applied though the class was set.
10. **`perspective` and any CSS `animation`/`transition` that animates `transform` both create a stacking context on whatever element they're set on**, for as long as `animation-fill-mode` holds it there (not just while actively animating). A sibling element positioned to overlap that one (e.g. the commander card's flip button sitting over the card image) can become unclickable even with `pointer-events: none` on its own icon, because the *ancestor* now stacks the whole overlapping region above the sibling. Fix: keep `perspective`/animated-`transform` rules on a dedicated inner wrapper, never on the same element an interactive sibling is positioned against — see the commander card's `.commander-card-perspective` split from `.commander-card-figure` above.
11. **A non-`none` `view-transition-name` forces its element into its own stacking context**, same as `perspective`/animated-`transform` above (gotcha #10) but easy to miss since nothing about the property *looks* stacking-related. `.site-header` has `view-transition-name: site-header` (so cross-page navigations treat it as one continuous element) but no explicit `z-index` — meaning that whole forced stacking context only ranked as `z-index: 0` among its siblings, so `.site-nav` right below it (`position: sticky; z-index: 20`) painted *over* it regardless of any `z-index` set on elements *inside* the header (the site-wide search dropdown's own `z-index: 60` couldn't escape it — a descendant's `z-index` only ever competes within its own stacking context, never past it). Fixed by giving `.site-header` itself an explicit `position: relative; z-index: 25` so the whole header, dropdown included, outranks the nav bar. Worth checking for on any other element that sets `view-transition-name` and later turns out to have positioned children needing to float above a later sibling.
12. **An animated (or merely non-`none`) `transform` on an ancestor becomes the containing block for a `position: fixed` descendant** — that descendant then positions itself relative to the *transformed ancestor's* box, not the viewport, defeating the entire point of `fixed`. Hit in `js/site-search.js`'s mobile search overlay: the close button is `position: fixed`, pinned to the exact px spot/size the trigger button occupies (via `getBoundingClientRect()`-derived CSS custom properties), but it originally lived inside `.site-search-bar`, which the entrance animation (`search-content-in`) applies `transform: scale(...)` to — mid-animation, the "fixed" button would have scaled and moved right along with the bar instead of staying stationary at the trigger's real position. Fixed by animating `.site-search-field` alone instead of the whole `.site-search-bar`, since the field doesn't need to stay put the way the close button does. Whenever a `position: fixed` element needs to stay genuinely pinned to the viewport, check every ancestor up to (but not including) the one it's meant to escape for an animated/set `transform` (or `filter`/`perspective`/`will-change` naming one of those) — not just whether the *element itself* has one.
13. **A `grid-template-rows: 0fr/1fr` collapse animation needs `overflow: hidden` on the collapsing grid item to work at all** (same reasoning as gotcha #1's clipping issue, but here the clipping is *load-bearing*, not incidental) — without it, the item's default `min-height: auto` keeps it rendered at full content height regardless of the row track's own animated size. That same `overflow: hidden` then clips any select/date popup that opens *inside* it, though, since those position themselves relative to their own field, a descendant of the clipping box — the popup gets cut off right at the (small, collapsed-content-height) box's own edge, which reads as "cut off by whatever page content happens to sit right above/below the filter box" rather than an overflow bug. Hit in `.filter-panel-clip` (Comandanti / Giocatori / Archetipi / Matchups's collapsible filter box, `js/filter-toggle.js`). Fixed by toggling the clipping itself, not just relying on `.cs-wrap.is-open`'s own `z-index: 30` (that only helps once a popup can actually escape its containing box, which `overflow: hidden` prevents outright, no z-index fixes that) — `.filter-panel-clip.is-open` switches to `overflow: visible` once the expand transition's own `transitionend` fires (confirmed still expanding, not right when the click happens, or a popup opened mid-animation would already escape while the row is still visually only partway open), and switches back to `hidden` immediately on collapse, before that animation starts, so the shrink itself still clips normally.

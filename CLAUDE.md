# duelcommanderpiacenza.github.io

Static site (vanilla HTML/CSS/JS, **no build step**, no framework, no bundler) for the Magic: the Gathering "Duel Commander Piacenza" player group — leagues, events, match results, commander/archetype stats, player standings. Backend is Supabase (Postgres + Auth + Storage). Hosted on GitHub Pages. Italian-language UI. **It isn't a club: never call it "il club" (or "del club") in any user-facing text** — say "Duel Commander Piacenza", or rephrase ("tra tutti i giocatori", "gli ultimi 10 eventi").

- `styles.css` — one shared stylesheet for the whole public site (~6000 lines). `admin/admin.css` is separate, loaded alongside it on admin pages.
- No React/Vue/etc. Pages are plain `.html` files; each loads `js/layout.js` (shared header/nav/search/theme/tooltips) plus one page-specific module — usually `js/*-page.js` or `js/*-detail.js`, but `index.html` uses `js/home.js` and `social.html` `js/moxfield.js` — mounted by `js/router.js` (see "In-app navigation"), not by a script tag of its own. **`sw.js` must stay at the site root**: a service worker only controls pages at or below its own folder, so moved into `js/` it would control nothing (GitHub Pages can't send the `Service-Worker-Allowed` header that would lift that), breaking the PWA install.
- **Nav markup is duplicated verbatim across every public page's `<head>`/`<body>` start** — there's no shared header partial, no server-side includes (GitHub Pages serves static files only). Changing the nav means editing all ~12 public HTML files individually (badges.html included, even though it has no tab of its own). Same for the PWA-related `<head>` tags (manifest link, apple-mobile-web-app-*, viewport-fit=cover).
- Two separate installable PWA identities: the public site (`manifest.json` at root) and the admin app (`admin/manifest.json`), each with their own icon set — admin's icons are the same club logo recolored black instead of red, both use `id`/`scope` to stay distinct as separate installs from the same origin.
- **New accent-colored UI elements (buttons, badges, small floating controls, etc.) should default to the brand-red family** (`--brand-red` and friends, `rgba(220, 24, 28, ...)` for translucent variants) rather than a neutral dark/gray tint — an explicit standing preference, not just this one element's choice. `.badge-status-open` and the commander-detail flip button are the existing examples to match.

## Data model (Supabase, see `supabase/schema.sql`)

No ORM — `js/db.js` is a thin wrapper: `Entity.method()` functions that `await` a Supabase query and throw on error. **PostgREST returns at most 1000 rows per response and silently truncates the rest** — any query that can grow past that (batches across events, whole-history lists) should go through db.js's `selectAllRows` (pages with `.range()`, needs a deterministic order ending on a unique column). `EventEntries.listAll` / `Matches.listAll` (auto-badge rules) are paged this way too. League pages, the Bacheca, badges **and Giocatori/Comandanti/Archetipi/Matchups** load events via `fetchEventsResults(eventIds)` — entries + matches in 2 paged requests per chunk of 100 event ids (the ids go in the URL, so a whole-history scope is chunked to stay under URL length limits), regrouped per event — rather than 2 requests per event; the Bacheca charts use `EventEntries.listForChartsSince` (date-filtered by the DB, only the columns they need). Deliberately **not** on event create: a new event starts open and empty, so no published result changes (its +1 to the league's X is picked up by the next trigger, e.g. closing it). Any new code path that closes/reopens an event or league must call it too. Always **fire-and-forget** (`.catch(console.error)`): the "Salvato." message appears before it finishes (several seconds). **Leaving or reloading the admin page meanwhile cuts it off** (the caches keep their old content — or, caught between a table's delete-all and insert-all, end up empty), so it shows a status bar while it runs (`.sync-status`, admin.css: "Aggiornamento di badge e statistiche… non chiudere la pagina" → green "aggiornati", red on failure, details in the console) and the browser asks before leaving (`beforeunload`). It **never runs twice at once**: a trigger during a run queues one more full run right after (two overlapping runs interleaved their delete-all/insert-all on the same tables, one failing on duplicate rows). The caches keep their previous content after a failure until the next trigger. Badge **delete** doesn't trigger it and needn't: `on delete cascade` drops that badge's cache rows. RLS: public read is scoped so an open (unpublished) event is only visible while its date is today or in the future (`is_open = false or event_date >= current_date`) — a "save the date" preview that disappears from public view once its day has passed and it's still not closed; entries/matches are gated to closed events only. Changes to an existing database go in `supabase/migrations/` (numbered, each with a rollback) **and** are folded into `schema.sql`, which stays the from-scratch setup. Running locally (localhost/127.0.0.1), `js/supabase-client.js` connects to the separate **dcp-dev** Supabase project instead of live, so local testing never touches real data. **Player login (Google accounts, claiming a player, the player card, admin "Utenti" tab) is live since 2026-10-05 (migrations 001–007 on both databases, `player-login` merged into `main`) — plan, decisions and history in `PLAYER_LOGIN.md`.**

## Shared JS conventions

- **`custom-select.js` / `custom-date.js`** — progressive-enhancement skins over native `<select>`/`<input type=date>`. Opt-in `data-searchable` on a `<select>` (the admin entry form's player/commander/partner and the match form's Giocatore 1/2) adds a search field at the top of its menu, filtering options as you type (case/accent-insensitive; the menu becomes a flex column so only the list scrolls; ↓/Enter reach the matches, Enter picks the first match only once something's typed). The native element stays the source of truth (`.value`, `change` events, `<option>` list) and is moved *inside* a new wrapper (`.cs-wrap`/`.cd-wrap`), hidden but functional. **This means a select/date field's actual DOM child, once enhanced, is that wrapper — not the original element directly** — matters for any CSS `:has(> select)`-style selector or JS querying `.field`'s direct children. `custom-date.js`'s trigger shows the native input's own `placeholder` attribute when empty (e.g. `placeholder="Dal"` on a from-date filter), falling back to the generic `"gg/mm/aaaa"` for any date input that never set one — opt-in, doesn't change any other date field's behavior. Likewise opt-in: a `data-open-on-today` attribute (all six "Dal" filter inputs) makes the popup always open on the **current** month instead of the selected value's month; admin form date fields don't set it, so editing an old event still opens on that event's month.

## Nav & responsive breakpoints

- **900px** — nav switches from wrapping tabs to a single horizontally-scrollable row.
- **Any touch device** (`html.nav-mobile`, see above) — nav becomes a floating pill fixed to the bottom of the screen; tapping it opens an upward panel listing all tabs. This is the *only* place safe-area-inset / overscroll-behavior fixes were added — desktop-without-touch is the only thing that still gets the normal nav. This intentionally also covers touch laptops/tablets/iPad now (not just phones) — an earlier, narrower version tried gating on `max-width: 640px` plus `pointer: coarse`/`hover: none`, which excluded those on purpose, but that media-query condition itself turned out to be unreliable on real phones (Samsung Internet) and was dropped entirely rather than patched further.
- **Reusable nav-submenu scaffolding, currently unwired**: `.nav-item-has-sub` / `.nav-sub-hint` / `.nav-submenu` / `.nav-sublink` in `styles.css` implement a full "tab with a hover popup on desktop, always-visible nested row on mobile" pattern. It was built and tried for nesting "Matchups" under "Comandanti", then reverted back to Matchups being its own top-level tab per product decision — but the CSS was deliberately left in place for the next tab that needs to nest under another one. To reuse: wrap a `<a class="nav-link">` + sibling `<div class="nav-submenu">` in `<div class="nav-item-has-sub">`, submenu children are `<a class="nav-sublink" data-nav="X">`; add a `body[data-active-nav="X"] .nav-sublink[data-nav="X"]` active-highlight rule (there's no generic one, it was removed with the Matchups wiring). Needs duplicating across all public pages' nav markup, same as any other nav change.

## Commander detail page: Scryfall card art

`commander.html`/`js/commander-detail.js` shows the commander's own Scryfall
card image next to its name, spanning from the title down to the bottom of
the stat tiles (desktop), or stacked below the title (mobile, ≤640px:
the title takes its whole line, the card centred on the page — auto margins
plus `left: -29px`, half the back button + gap, since `.page-heading`
starts right of it; player.html's card is centred the same way).

- **Fetch**: `fetchScryfallCard(name)` does a real JSON `fetch()` to
  `/cards/named?exact=...` (not the simpler `format=image` redirect trick)
  because a double-faced commander needs both faces' own `image_uris` to
  flip between, not just one. `scryfallCardImages(card)` distinguishes true
  double-faced cards (`card_faces[].image_uris` present on every face) from
  split/adventure/flip cards (a single combined image, `card.image_uris`
  only) — that's the actual signal for whether the flip button appears, not
  just the presence of `card_faces`. Loaded independently of the page's own
  Supabase data (not awaited) — a slow/unreachable Scryfall never blocks the
  real page, a failed/no-match lookup just leaves the figure hidden.
- **Sizing**: `syncCardImageLayout()` sets the image's height in JS (px,
  measured from `.page-heading`'s top to the stat tiles' bottom — two
  separate elements with no CSS-only way to span between them), then reads
  the image's own resulting width back and sets it as
  `.commander-top-row-main`'s `padding-right`, so the stat tiles grow right
  up to the card's real (height-dependent) edge instead of stopping short
  at a fixed guess. The other side never comes from the downloaded image:
  `.commander-card-face` has `aspect-ratio: 488 / 680` + `object-fit:
  cover`, so the box is always Scryfall's card shape (same as the
  placeholder, the album carousel's slots and the player card) whatever
  image arrives.
- **Reveal timing**: the Scryfall image and the Supabase winrate stats load
  independently in unpredictable order — revealing the card as soon as
  either one alone is ready risks measuring/sizing against the other's
  still-showing placeholder. A `cardImageReady`/`statsReady` two-flag latch
  (`revealCardIfReady()`) holds the card hidden until both are true.
- **Collapsible filters that don't move the page**: the Lega/Evento/Dal row sits in a `.filter-panel.detail-filter-panel` (shared with player.html when it shows a player card) toggled by the shared `filter-toggle.js` button right after the "Statistiche" title (`.stats-heading`, shared with player.html), in the same `.filter-panel-body` box as the list pages, defaulting its "Dal" to 2 years ago like them (narrows the stat tiles), but unlike the list pages it never collapses in height — collapsed, it just fades out (plus `visibility: hidden`) and the stat tiles slide up into its space via `transform: translateY(var(--commander-filters-shift))` (set by `syncFiltersShift()` to the row's exact layout height). Desktop only: on phones (≤640px, where the card stacks above the stats instead of beside them) the row collapses for real like the list pages' panels and the rest of the page moves up. On desktop the layout never changes, so the card (sized from *layout* positions via `layoutTop()`/`offsetTop`, which ignore transforms — not `getBoundingClientRect`) keeps its size and nothing below moves. Its CSS rules are written as `.filter-panel.detail-filter-panel…` on purpose: the shared `.filter-panel` rules come later in the file with equal specificity and would otherwise win (really collapsing the row).
- **Loading placeholder**: `#commander-card-skeleton` (`.commander-card-skeleton`, brand-red shimmer) sits from first paint in the card's exact spot and size — same positioning as the figure, Scryfall "normal" proportions (`aspect-ratio: 488/680`), height set by the same `syncCardImageLayout`, whose padding-right uses the *placeholder's* width while it's showing — so neither the phone layout (card stacked in-flow below the title) nor the desktop stats move when the real card replaces it (`revealCardIfReady` hides it). `dropCardPlaceholder()` removes it when there's no image (Scryfall miss / image error), and the stats then take the full width.
- **Flip (double-faced cards only)**: a real CSS 3D flip (`.commander-card-flipper`
  toggling `.is-flipped { transform: rotateY(180deg) }`, both faces stacked
  as separate `<img>`s with `backface-visibility: hidden`), not a
  swap-on-click. `perspective` and the entrance animation both live on a
  dedicated `.commander-card-perspective` wrapper *one level below*
  `.commander-card-figure`, never on the figure itself — either one directly
  on the figure creates a stacking context that broke click-through to the
  sibling flip button, even with `pointer-events: none` on its icon (see
  gotcha #10).
- **Mobile title fit** (shared `js/page-title-fit.js`, also used by
  `league.html`/`event.html` — on phones their title pills, "In corso" /
  "Top 8", are stacked onto their own line below the name by styles.css,
  so only the name itself is fitted; were a fixed-size pill ever on the
  same line, its width is subtracted from the calculation instead of scaled):
  `fitTitleToOneLine()` shrinks `#commander-title`'s
  font-size (down to a 17px floor) when the name (no colour pips in this title any more: the card shows the colours)
  don't fit the width actually left next to the back button on a phone,
  measured against the text's own natural unwrapped width — not a fixed
  smaller mobile font-size, so short names stay full-size and only long
  ones shrink, only as much as they need to. Paired with
  `alignBackButtonToTitle()`: `.page-heading-row`'s mobile
  `align-items: flex-start` only top-aligns the back button with the
  title (needed so it anchors to the name, not the card image stacked
  below it on mobile) — once the title's own font-size shrinks well below
  the button's 44px, top-aligning no longer puts their *centers* level.
  This nudges the button's `margin-top` by the exact difference so it
  stays vertically centered against whatever the title's actual rendered
  height ends up being.

## Animation conventions

- **`entrance-fade-up`** (`opacity 0→1` + `translateY(10px)→none`, 380ms `cubic-bezier(0.2, 0.8, 0.2, 1)`) is the default "this just appeared" animation — `.card`, `.entity-card`, `.data-table-wrap`, `.dashboard-league-card`/`-chip`, `.dashboard-event-row` (the Calendario overlay's rows), `.upcoming-row` (Bacheca "Prossimi"/"Ultimi eventi" rows), `.league-group` (Leghe & Eventi cards), `.stat-tile`, `.pie-chart-wrap` (covers every chart shape, including the SVG line chart, since they all share that wrapper), `.bar-chart-row`, `.badge-card`, `input[type="search"]`, `.admin-topbar h1`, and on desktop commander.html's/player.html's open-by-default filter panel (`backwards` fill only, so it never overrides the panel's own fade-out afterwards; hidden by `body.is-loading` until the reveal, since its own `visibility: visible` would otherwise show through the hidden loading region). Reach for this one before inventing a new keyframe for "a card/row/tile just rendered".
- **Page-load reveal, all at once**: every public page's `body` starts with class `is-loading`; `body.is-loading * { animation-play-state: paused }` freezes every animated element (anything using `entrance-fade-up` or similar) at its first frame the instant it's inserted, however long before the page is actually "ready". `js/page-loading.js`'s `hidePageLoading()` removes `is-loading` at the same moment it fades out the splash overlay, so every element's entrance plays together, in sync, rather than each finishing invisibly off in the background the moment it happened to render. **Catch: an `animation` shorthand resets `animation-play-state` to running, so an entrance animation declared with a selector that outranks `body.is-loading *` (0,1,1) — an id, two or more classes, or a `:not(#id)` — is *not* paused: it plays and finishes unseen while the page loads. Each of those needs its own `body.is-loading <selector> { animation-play-state: paused }` in the list right after that rule** (there: the detail pages' filter panels, player.html's card, the list pages' search box). **Any new element given an entrance animation must also be added to the `@media (prefers-reduced-motion: reduce)` block right after the stagger `:nth-child` group in `styles.css` (the one listing `.card`, `.data-table-wrap`, … `.badge-card`, `.upcoming-row`, `.league-group`, `.bar-chart-row`, `.filter-toggle-btn` — its `animation: none` is `!important` on purpose: most of those elements declare their animation later in the file, which would otherwise win on source order and keep animating for reduced-motion visitors) that sets `animation: none`** on this same list — otherwise a motion-reduced visitor never sees it at all (the animation is disabled, which for a *paused* animation means it stays stuck at its invisible first frame forever, not "instantly visible" as reduced-motion is supposed to mean). This exact gap is what caused detail-page titles to stay invisible through an entire page load for reduced-motion users before that specific animation was removed (see the "titles" guideline below).
- **Staggered cascade**: a fixed `:nth-child(2)`…`:nth-child(5)`, `:nth-child(n + 6)` selector group (45ms/90ms/135ms/180ms/225ms `animation-delay`, capped at 6 steps rather than queuing a long list one-by-one) is shared by every repeating grid/list of cards — `.entity-card`, `.dashboard-league-card`, `.dashboard-league-chip`, `.dashboard-event-row`, `.stat-tile`, `.badge-card`. Add a new repeating item type to this *same* selector group rather than writing its own stagger rule. (A different stagger convention — inline `style="animation-delay: ${i * 60}ms"` set from JS — is used instead for `.pie-legend-item` and `.bar-chart-row` rows (`js/metagame-chart.js`), since those come from a dynamically-sized array with no natural CSS `:nth-child` cap; match whichever convention fits the situation, don't mix both on one element type.)
- **Popup/dropdown open**: `cs-menu-in` (custom-select) and `cd-popup-in` (custom-date) — both `opacity 0→1` + `translateY(-4px)→none`, 140ms `ease` — are the shared "small panel opening beneath a trigger" animation (`.matchups-dropdown` reuses `cs-menu-in` directly rather than defining its own). `nav-dropdown-panel-in`/`-out` (mobile nav popup) and `search-circle-in`/`-out` (mobile full-screen search, see below) are closer cousins of this same idea for their own, more specific shapes.
- **Hero pages before their colour arrives: neutral, not red** (styles.css, after `body.has-hero-accent`): while `main[data-accent-from-hero]` has no `.has-hero-accent` yet (not account.html's signed-out view), `body` redefines the site's red variables to a warm grey (`#5b5552` / `#45403e`; dark mode light-grey text), the desktop bar's gradient (`--bar-c1/-c2`) goes charcoal, the dark nav pill and "Torna all'inizio" lose their red-brown, and the hero's own starting background and its loading placeholder (`.sk-hero`) are grey too — so taking the art's colour (applyHeroTone, its own 450ms blends) reads as a soft blend from grey, not a jump from red. A page that never gets a colour (no art) stays grey. The red buttons' glows follow their own colour too (`.btn-primary`, account's ✎ `.pc-edit-btn`, `.decklist-icon`: `color-mix(in srgb, var(--brand-red) N%, transparent)` — the same red on other pages), not a fixed red. The loading shimmers too: the page placeholders (`.sk`), the commander card's (`.commander-card-skeleton`) and the Album's loading cards (`.cmd-carousel-slide.is-loading`) mix `var(--brand-red)` (dark mode: `var(--brand-red-deep)`, its light shade) — red elsewhere, grey then the hero's colour on hero pages; the hero's own card placeholder stays white on its art, dark mode included. **A new red element's shadow / tint should mix `var(--brand-red)`, never a literal red**, or it stays red on hero pages.
- **Comandanti / Giocatori lists, the record as a bar**: `historyStatsHtml`'s stats take `record` (`[wins, losses, draws]`) — a thin green / grey / red bar in the "V-S-P" label's place (`.history-stat-record`; the label visually hidden, the words on hover), no extra height. Other lists using historyStatsHtml are unchanged. (Tried and dropped: the winrate as a pill tinted by value, a small ring before it, and a colour-identity strip on the Comandanti rows.)
- **Loading placeholders (skeletons) instead of a "Caricamento..." splash**: every public page's `#page-loading-overlay` holds a static `.sk-page` (`aria-hidden`; a modifier per page: `is-home`, `is-events`, `is-list`, `is-matchups`, `is-tiles`, `is-cards`, `is-hero` — account.html's with `is-account`: its real hero is in the signed-in view, `display: none` while loading, so the placeholder hero pulls itself up to the bar with its own -28px / -20px) drawing that page's layout as soft shimmering blocks (`.sk` + `.sk-hero` / `.sk-tabs` / `.sk-title` / `.sk-search` / `.sk-row` / `.sk-chart` / `.sk-cols` + `.sk-col` / `.sk-tl` / `.sk-ev-board` / `.sk-grid` / `.sk-card` / `.sk-matrix`; styles.css right after the overlay rules). Hero pages: `.sk-hero` placed like the real hero (hanging from the bar on a computer; edge to edge under the transparent header on touch screens, `--hero-bleed` wider than 640px), and the touch back pill stays above it (`z-index: 6` while loading). **`.sk-hero.has-card`**: the card's column too, laid out like `.profile-hero-inner` (280px card beside the text; from 820px down the name, the card — 240px on phones, account's 260px — and the numbers, centred) — static on commander.html and account.html (always a card), added by js/player-detail.js on player.html as soon as its card request says the player shows one (before the page is revealed), so a hero with a card isn't revealed at the no-card height. The hero's bars follow the real text: the name (`.sk-hero-title`), a `.sk-hero-line` only where the hero has a second line (league's status and dates, event's details; above the name on account, its kicker), the stat chips. `.sk-touch-only` (the segmented controls) is hidden off touch screens; `.sk-cols`' second column only on a computer wider than 860px. The `<p>Caricamento...</p>` stays for screen readers (visually hidden); `.is-stuck` hides the placeholders and shows that message plus the reload button. The shimmer is `background-attachment: fixed` (one wave for the whole screen) and declared as `.page-loading-overlay .sk` so it outranks the `body.is-loading *` pause; none with reduced motion. **A page whose layout changes should have its `.sk-page` markup updated to match.**
- **Data errors (`js/ui.js` `showError`)**: "Si è verificato un errore nel caricamento dei dati." with a **"Riprova"** button under it (`.page-error-box`, `.page-error-retry` → `location.reload()`). Seen mostly when the installed app is reopened or a browser restores the tab while the phone's connection is still coming back: nothing retries a failed Supabase request (the service worker caches nothing, so it isn't a cache issue).
- **Closing/hiding needs its own explicit choreography — CSS cannot transition `display`.** A `display: none ↔ flex/block` toggle (the base state for anything that's conditionally shown) jumps instantly; there's no way to animate *into* that closed state directly. The established pattern, used in three places now, is: add an `is-closing` class (distinct from `is-open`) that keeps the element rendered with `display` still set, playing a reverse/exit animation; listen for that animation's `animationend` (or, for the splash overlay, `transitionend`) and only *then* let the element actually disappear (remove the class / let the "closed" `display: none` rule apply again / remove the element outright).
  - `js/page-loading.js`'s `hidePageLoading()` — adds `.is-hidden` (opacity transition), removes the splash element on `transitionend`.
  - `js/nav-dropdown.js` — mobile nav popup panel, `.is-closing` + `nav-dropdown-panel-out`. It also slides the touch nav pill away on scroll down / back on scroll up (`.site-nav.is-scrolled-away`, `bottom` animated; never while the panel is open, always near the top — except on reaching the page's bottom while scrolling down, which hides it however little the page scrolls). On touch screens every page's `.page-main` is at least a screen tall (`min-height: 100lvh`), so a short page's footer starts just below the screen and is only seen by scrolling down to it — which slides the pill off it. No red backdrop behind the pill any more — a deep two-layer shadow on the pill instead.
  - `js/site-search.js` — mobile full-screen search overlay, `.is-closing` + `search-circle-out`.
  - Any new dismissible mobile panel/overlay should follow this same `is-open`/`is-closing` + `animationend` shape rather than inventing another way to animate an exit. The two animation-based ones (`nav-dropdown.js`, `site-search.js`) also independently check `prefers-reduced-motion` in JS before starting the choreography at all (`page-loading.js` doesn't: under reduced motion the overlay's `transition: none` means its `transitionend` never fires, so the faded-out splash just stays in the DOM at opacity 0 with `pointer-events: none` — harmless, but it's never removed) (not just disabling the animation in CSS) — skipping straight to the closed state instead — because `animationend` never fires for an animation that a reduced-motion CSS rule disabled, which would otherwise leave the element stuck in its `is-closing` (still-rendered) state forever.
- **`search-circle-in`/`-out`** (`js/site-search.js`, mobile only): the full-screen search overlay expands from/collapses back into the round trigger button's own on-screen position via animated `clip-path: circle(... at var(--search-origin-x) var(--search-origin-y))`, rather than a plain fade — reads as growing out of the button that opened it. The origin coordinates and `--search-max-radius` (the exact distance from that point to the farthest viewport corner, guaranteeing full coverage regardless of where the trigger sits) are computed in JS via `getBoundingClientRect()` and set as CSS custom properties on open **and** on close (not cached from open — an orientation change while the overlay is open would otherwise leave it animating from a stale point). The close button is pinned to that same rect (`--search-close-top`/`-right`/`-size`) via `position: fixed`, at the trigger's own real size/spot — it reads as "the same button, still there" rather than a second close affordance appearing once the overlay opens, so it deliberately does **not** animate in; only `.site-search-field` cascades in a beat later, via `search-content-in` (scale 0.85→1 + fade, same easing curve as the circle itself) rather than the generic `entrance-fade-up` — a slide-up-from-below reads as an unrelated, second animation bolted onto a circular reveal; a scale-in (things coalescing into place) continues the same "expanding from a point" motion instead. Prefer matching an element's own animation's *shape*/vocabulary (expand vs. slide vs. fade) to whatever's already happening around it, not just reusing the nearest existing keyframe by default. (The animation deliberately targets `.site-search-field`, not the whole `.site-search-bar` the close button also lives in markup-wise — see gotcha #12: an animated `transform` on an ancestor of a `position: fixed` element hijacks its containing block.)
- **Commander card flip/entrance** (`commander-card-in`, `.commander-card-perspective`): see gotcha #10 below — `perspective` and any animated `transform` force a stacking context onto whatever element they're set on, so both live on a dedicated wrapper *one level below* the actual card figure, never directly on an element with an interactive sibling that needs to stay clickable over it.
- **Titles should generally *not* be animated, and should not be hidden/gated behind the page's loading state either.** `.page-heading h1` (the `<h1>` on every commander/player/event/league detail page) deliberately has **no** entrance animation, unlike `.admin-topbar h1` (which keeps `entrance-fade-up`, since admin tab headers are always static text, never swapped). The difference: a detail page's `<h1>` starts as a plain "Caricamento..." placeholder and gets overwritten in place once the entity's name loads — animating that swap, or hiding it until "ready" (both were tried and reverted this session), makes the transition itself feel like a deliberate, designed part of the page instead of what it actually is: a title that's simply there from the first frame and updates like any other text would. The name genuinely isn't known before that first fetch resolves, so a brief "Caricamento..." is an accepted, deliberate trade-off — not a bug to keep re-solving with cleverer CSS. Default to this same "no animation, no hiding, just let it update" treatment for any other element that's read as *always there* rather than *newly appeared* (page titles, persistent labels) — reserve entrance animations for content that's genuinely new on screen (cards, rows, charts, popups).

## Non-obvious gotchas (hit and fixed this session — avoid repeating)

**General rule, not just a gotcha — worth applying proactively, not only when something visibly breaks**: any popup/dropdown/tooltip (a select's own menu, a date picker, a search dropdown, a table-cell tooltip, a close button meant to float above everything) must reliably paint above ordinary static page content around it — chart cards, data tables, nav bars, whatever else happens to be a sibling or nearby ancestor. This site has hit the *same underlying failure* from several different specific causes now (gotchas #1, #2, #10, #11, #12, #13 below) — an `overflow: hidden` ancestor clipping it outright, a stacking context accidentally trapping its `z-index` below a later sibling, an animated `transform` hijacking a `position: fixed` element's containing block. When adding any new popup-like UI, don't just give it a z-index and assume it works — actively check: (a) does every ancestor between it and the page root allow `overflow: visible` at the moment it's shown (not necessarily always, e.g. during a collapse animation), and (b) does any ancestor's `animation`/`transition`/`transform`/`filter`/`perspective`/`view-transition-name` force an unintended stacking context that caps its `z-index` below whatever it needs to outrank.

1. **`overflow: hidden` on an element clips its own `::before`/`::after` too**, even ones meant to render outside its box (tooltips, dropdown shadows). If an element needs both truncation (`text-overflow: ellipsis`) *and* to host an absolutely-positioned popup/tooltip, put the truncation on an inner wrapper instead and keep the outer element unclipped.
2. **A scrolling container's `overflow-x: auto` forces `overflow-y` to also clip** (per the CSS overflow spec, whichever axis isn't explicitly set gets forced to `auto`/clipping too once the other is non-`visible`). A tooltip/popup anchored inside a horizontally-scrolling table (`.matchups-matrix-wrap`) cannot escape that clipping with CSS alone — it has to be a real element positioned via JS (`getBoundingClientRect`) and appended to `<body>`, outside the clipping ancestor. Use the shared `js/floating-tooltip.js` (`attachHoverTooltips(container, selector, textFor)` — the site's only tooltip: badges/banned icon/"Top 8" pill site-wide via `js/layout.js`, the Matchups headers and the Comandanti bar-chart labels; `fullTextIfTruncated` shows it only when a label is actually cut off; hover + keyboard focus; on touch, a tap on a badge inside a link card only shows its tooltip — `js/layout.js` cancels the link's click in the capture phase, mouse clicks still follow it).
3. **`mouseenter`/`mouseleave` don't bubble**, so event-delegation on a parent needs the capture phase (`addEventListener(type, fn, true)`). And if the hovered element has a child (e.g. a truncation `<span>` inside a `<th>`), capture-phase mouseenter/mouseleave fire *separately* for the child too as the cursor crosses that inner boundary — guard against re-triggering show/hide by tracking the currently-active target and checking `relatedTarget` on leave.
4. **`display: inline-flex` doesn't imply column direction.** A flex wrapper with two `width: 100%` children (e.g. a nav link + its submenu, in the mobile always-visible layout) needs an explicit `flex-direction: column` override, or the children sit side by side and the second one gets pushed off-screen — invisible, not just misaligned, if the ancestor also has `overflow-x: hidden`.
5. **Android's adaptive-icon system shrinks a non-`maskable` PWA icon defensively** (lots of padding) since it doesn't know how a launcher will crop it. A `purpose: "maskable"` icon variant with content filling ~70–80% of the canvas (this site uses 70%) against an opaque background fixes it — transparent backgrounds don't work for maskable icons, the OS crops the full square regardless.
6. **`beforeinstallprompt` (and the custom "Install app" banner built on it) is Chrome/Android-only** — Safari/WebKit has never implemented it, on iPhone or iPad. Don't expect it to fire there; the only install path on iOS is the manual Share → "Add to Home Screen".
7. Service worker (`sw.js`) is a deliberate no-op (pure network pass-through, no caching) — it exists only to satisfy Chrome's PWA installability check, since the site's data is always-live from Supabase and caching would show stale results.
8. **A generic dark-mode override can win on specificity over a more specific context rule that resets a background to transparent**, even when that rule is more semantically "specific." The generic dark-mode "give this a faint card background" rules (`styles.css`, the big `:root[data-theme="dark"] .card, .stat-tile, .pie-chart-wrap, ...` list) are 3 classes; a narrower "this one shouldn't have its own background, it's nested inside another card" rule like `.dashboard-card-commanders .pie-chart-wrap { background: none; }` is usually only 2 — the generic rule wins regardless of source order, silently reintroducing a visible background the narrower rule was trying to remove. Hit **three separate times** this session with this exact shape (`html.nav-mobile .site-nav`, `admin/admin.css`'s `.admin-tabs`, and `.dashboard-card-commanders .pie-chart-wrap`) — worth checking for this pattern by default whenever a "make this transparent/none in context X" rule doesn't seem to be working in dark mode specifically. Fix is always the same: a compound selector combining `:root[data-theme="dark"]` (or `html[data-theme="dark"]`) with the narrower context class(es) in one selector, placed near the other dark-mode overrides, not just relying on cascade order.
9. **Wrapping already-class-gated CSS in a redundant `@media` condition means BOTH have to independently match, and they can disagree.** The mobile-pill CSS was originally inside `@media (max-width: 640px) and (pointer: coarse) and (hover: none) { html.nav-mobile .site-nav { ... } }` — belt-and-suspenders with the JS-set class, in theory. In practice, some browsers (Samsung Internet) misreport `pointer`/`hover`, so the `@media` condition silently failed to match even when `html.nav-mobile` was correctly set by JS — the styling just never applied, with no error, nothing to debug from the DOM (the class was right there). Fixed by dropping the `@media` wrapper entirely and trusting the JS-set class as the single source of truth, rather than trying to patch the media query further.
10. **`perspective` and any CSS `animation`/`transition` that animates `transform` both create a stacking context on whatever element they're set on**, for as long as `animation-fill-mode` holds it there (not just while actively animating). A sibling element positioned to overlap that one (e.g. the commander card's flip button sitting over the card image) can become unclickable even with `pointer-events: none` on its own icon, because the *ancestor* now stacks the whole overlapping region above the sibling. Fix: keep `perspective`/animated-`transform` rules on a dedicated inner wrapper, never on the same element an interactive sibling is positioned against — see the commander card's `.commander-card-perspective` split from `.commander-card-figure` above.
11. **A non-`none` `view-transition-name` forces its element into its own stacking context**, same as `perspective`/animated-`transform` above (gotcha #10) but easy to miss since nothing about the property *looks* stacking-related. `.site-header` has `view-transition-name: site-header` (so cross-page navigations treat it as one continuous element) but no explicit `z-index` — meaning that whole forced stacking context only ranked as `z-index: 0` among its siblings, so `.site-nav` right below it (`position: sticky; z-index: 20`) painted *over* it regardless of any `z-index` set on elements *inside* the header (the site-wide search dropdown's own `z-index: 60` couldn't escape it — a descendant's `z-index` only ever competes within its own stacking context, never past it). Fixed by giving `.site-header` itself an explicit `position: relative; z-index: 25` so the whole header, dropdown included, outranks the nav bar. Worth checking for on any other element that sets `view-transition-name` and later turns out to have positioned children needing to float above a later sibling.
12. **An animated (or merely non-`none`) `transform` on an ancestor becomes the containing block for a `position: fixed` descendant** — that descendant then positions itself relative to the *transformed ancestor's* box, not the viewport, defeating the entire point of `fixed`. Hit in `js/site-search.js`'s mobile search overlay: the close button is `position: fixed`, pinned to the exact px spot/size the trigger button occupies (via `getBoundingClientRect()`-derived CSS custom properties), but it originally lived inside `.site-search-bar`, which the entrance animation (`search-content-in`) applies `transform: scale(...)` to — mid-animation, the "fixed" button would have scaled and moved right along with the bar instead of staying stationary at the trigger's real position. Fixed by animating `.site-search-field` alone instead of the whole `.site-search-bar`, since the field doesn't need to stay put the way the close button does. Whenever a `position: fixed` element needs to stay genuinely pinned to the viewport, check every ancestor up to (but not including) the one it's meant to escape for an animated/set `transform` (or `filter`/`perspective`/`will-change` naming one of those) — not just whether the *element itself* has one.
13. **A `grid-template-rows: 0fr/1fr` collapse animation needs `overflow: hidden` on the collapsing grid item to work at all** (same reasoning as gotcha #1's clipping issue, but here the clipping is *load-bearing*, not incidental) — without it, the item's default `min-height: auto` keeps it rendered at full content height regardless of the row track's own animated size. That same `overflow: hidden` then clips any select/date popup that opens *inside* it, though, since those position themselves relative to their own field, a descendant of the clipping box — the popup gets cut off right at the (small, collapsed-content-height) box's own edge, which reads as "cut off by whatever page content happens to sit right above/below the filter box" rather than an overflow bug. Hit in `.filter-panel-clip` (Comandanti/Giocatori/Archetipi's collapsible filter box, `js/filter-toggle.js`). Fixed by toggling the clipping itself, not just relying on `.cs-wrap.is-open`'s own `z-index: 30` (that only helps once a popup can actually escape its containing box, which `overflow: hidden` prevents outright, no z-index fixes that) — `.filter-panel-clip.is-open` switches to `overflow: visible` once the expand transition's own `transitionend` fires (confirmed still expanding, not right when the click happens, or a popup opened mid-animation would already escape while the row is still visually only partway open), and switches back to `hidden` immediately on collapse, before that animation starts, so the shrink itself still clips normally.

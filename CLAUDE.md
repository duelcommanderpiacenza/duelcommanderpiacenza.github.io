# duelcommanderpiacenza.github.io

Static site (vanilla HTML/CSS/JS, **no build step**, no framework, no bundler) for the Magic: the Gathering "Duel Commander Piacenza" player group — leagues, events, match results, commander/archetype stats, player standings. Backend is Supabase (Postgres + Auth + Storage). Hosted on GitHub Pages. Italian-language UI. **It isn't a club: never call it "il club" (or "del club") in any user-facing text** — say "Duel Commander Piacenza", or rephrase ("tra tutti i giocatori", "gli ultimi 10 eventi").

- **The stylesheet is `css/` — six files, `1-base-header-home.css` … `6-dark-tabbar-transitions.css`** (since 2026-10-16: the old single `styles.css`, ~16k lines, split **in its original order**, so the cascade is unchanged): loaded in that order by every public page (the `<link>`s are in `partials/head.html`) and by `admin/index.html` (before `admin/admin.css`). **Keep the order; later rules win ties** — a rule's place in its file, and the file's number, matter. The names say roughly what each mostly holds, but areas are interleaved (that's why it wasn't reorganised by area — moving rules could change which one wins). `url(...)` inside them is relative to `css/` (`../dc_pc.svg`). **Everywhere in this file and in code comments, "styles.css" means these files** (search them for the quoted section names).
- No React/Vue/etc. Pages are plain `.html` files; each loads `js/layout.js` (shared header/nav/search/theme/tooltips) plus one page-specific module — usually `js/*-page.js` or `js/*-detail.js`, but `index.html` uses `js/home.js` and `social.html` `js/moxfield.js` — mounted by `js/router.js` (see "In-app navigation"), not by a script tag of its own. **`sw.js` must stay at the site root**: a service worker only controls pages at or below its own folder, so moved into `js/` it would control nothing (GitHub Pages can't send the `Service-Worker-Allowed` header that would lift that), breaking the PWA install.

## Data model (Supabase, see `supabase/schema.sql`)

No ORM — `js/db.js` is a thin wrapper: `Entity.method()` functions that `await` a Supabase query and throw on error. **PostgREST returns at most 1000 rows per response and silently truncates the rest** — any query that can grow past that (batches across events, whole-history lists) should go through db.js's `selectAllRows` (pages with `.range()`, needs a deterministic order ending on a unique column). `EventEntries.listAll` / `Matches.listAll` (auto-badge rules) are paged this way too. League pages, the Bacheca, badges **and Giocatori/Comandanti/Archetipi/Matchups** load events via `fetchEventsResults(eventIds)` — entries + matches in 2 paged requests per chunk of 100 event ids (the ids go in the URL, so a whole-history scope is chunked to stay under URL length limits), regrouped per event — rather than 2 requests per event; the Bacheca charts use `EventEntries.listForChartsSince` (date-filtered by the DB, only the columns they need). Running locally (localhost/127.0.0.1), `js/supabase-client.js` connects to the separate **dcp-dev** Supabase project instead of live, so local testing never touches real data. **Serve it with `python scripts/serve.py` (port 8000), not `python -m http.server`**: the plain server sends no caching header, so the browser keeps its own copies for a while and, as files are edited, mixes old and new scripts — an old module missing an export the new one imports shows as the page's "errore nel caricamento" (fine after a reload); scripts/serve.py sends `Cache-Control: no-cache`. ## Shared JS conventions

- **`custom-select.js` / `custom-date.js`** — progressive-enhancement skins over native `<select>`/`<input type=date>`. Opt-in `data-searchable` on a `<select>` (the admin entry form's player/commander/partner and the match form's Giocatore 1/2) adds a search field at the top of its menu, filtering options as you type (case/accent-insensitive; the menu becomes a flex column so only the list scrolls; ↓/Enter reach the matches, Enter picks the first match only once something's typed). The native element stays the source of truth (`.value`, `change` events, `<option>` list) and is moved *inside* a new wrapper (`.cs-wrap`/`.cd-wrap`), hidden but functional. **This means a select/date field's actual DOM child, once enhanced, is that wrapper — not the original element directly** — matters for any CSS `:has(> select)`-style selector or JS querying `.field`'s direct children. `custom-date.js`'s trigger shows the native input's own `placeholder` attribute when empty (e.g. `placeholder="Dal"` on a from-date filter), falling back to the generic `"gg/mm/aaaa"` for any date input that never set one — opt-in, doesn't change any other date field's behavior. Likewise opt-in: a `data-open-on-today` attribute (all six "Dal" filter inputs) makes the popup always open on the **current** month instead of the selected value's month; admin form date fields don't set it, so editing an old event still opens on that event's month.

## Commander detail page: Scryfall card art

`commander.html`/`js/commander-detail.js` shows the commander's own Scryfall
card image next to its name, spanning from the title down to the bottom of
the stat tiles (desktop), or stacked below the title (mobile, ≤640px:
the title takes its whole line, the card centred on the page — auto margins
plus `left: -29px`, half the back button + gap, since `.page-heading`
starts right of it; player.html's card is centred the same way).

- **Fetch**: `fetchScryfallCard(name)` does a real JSON `fetch()` to
  `/cards/named?exact=...` (not the simpler `format=image` redirect trick)
  because a double-faced commander needs both faces' own `image_uris` to
  flip between, not just one. `scryfallCardImages(card)` distinguishes true
  double-faced cards (`card_faces[].image_uris` present on every face) from
  split/adventure/flip cards (a single combined image, `card.image_uris`
  only) — that's the actual signal for whether the flip button appears, not
  just the presence of `card_faces`. Loaded independently of the page's own
  Supabase data (not awaited) — a slow/unreachable Scryfall never blocks the
  real page, a failed/no-match lookup just leaves the figure hidden.
- **Sizing**: `syncCardImageLayout()` sets the image's height in JS (px,
  measured from `.page-heading`'s top to the stat tiles' bottom — two
  separate elements with no CSS-only way to span between them), then reads
  the image's own resulting width back and sets it as
  `.commander-top-row-main`'s `padding-right`, so the stat tiles grow right
  up to the card's real (height-dependent) edge instead of stopping short
  at a fixed guess. The other side never comes from the downloaded image:
  `.commander-card-face` has `aspect-ratio: 488 / 680` + `object-fit:
  cover`, so the box is always Scryfall's card shape (same as the
  placeholder, the album carousel's slots and the player card) whatever
  image arrives.
- **Reveal timing**: the Scryfall image and the Supabase winrate stats load
  independently in unpredictable order — revealing the card as soon as
  either one alone is ready risks measuring/sizing against the other's
  still-showing placeholder. A `cardImageReady`/`statsReady` two-flag latch
  (`revealCardIfReady()`) holds the card hidden until both are true.
- **Loading placeholder**: `#commander-card-skeleton` (`.commander-card-skeleton`, brand-red shimmer) sits from first paint in the card's exact spot and size — same positioning as the figure, Scryfall "normal" proportions (`aspect-ratio: 488/680`), height set by the same `syncCardImageLayout`, whose padding-right uses the *placeholder's* width while it's showing — so neither the phone layout (card stacked in-flow below the title) nor the desktop stats move when the real card replaces it (`revealCardIfReady` hides it). `dropCardPlaceholder()` removes it when there's no image (Scryfall miss / image error), and the stats then take the full width.
- **Flip (double-faced cards only)**: a real CSS 3D flip (`.commander-card-flipper`
  toggling `.is-flipped { transform: rotateY(180deg) }`, both faces stacked
  as separate `<img>`s with `backface-visibility: hidden`), not a
  swap-on-click. `perspective` and the entrance animation both live on a
  dedicated `.commander-card-perspective` wrapper *one level below*
  `.commander-card-figure`, never on the figure itself — either one directly
  on the figure creates a stacking context that broke click-through to the
  sibling flip button, even with `pointer-events: none` on its icon (see
  gotcha #10).
- **Mobile title fit** (shared `js/page-title-fit.js`, also used by
  `league.html`/`event.html` — on phones their title pills, "In corso" /
  "Top 8", are stacked onto their own line below the name by styles.css,
  so only the name itself is fitted; were a fixed-size pill ever on the
  same line, its width is subtracted from the calculation instead of scaled):
  `fitTitleToOneLine()` shrinks `#commander-title`'s
  font-size (down to a 17px floor) when the name (no colour pips in this title any more: the card shows the colours)
  don't fit the width actually left next to the back button on a phone,
  measured against the text's own natural unwrapped width — not a fixed
  smaller mobile font-size, so short names stay full-size and only long
  ones shrink, only as much as they need to. Paired with
  `alignBackButtonToTitle()`: `.page-heading-row`'s mobile
  `align-items: flex-start` only top-aligns the back button with the
  title (needed so it anchors to the name, not the card image stacked
  below it on mobile) — once the title's own font-size shrinks well below
  the button's 44px, top-aligning no longer puts their *centers* level.
  This nudges the button's `margin-top` by the exact difference so it
  stays vertically centered against whatever the title's actual rendered
  height ends up being.

## Animation conventions

- **`entrance-fade-up`** (`opacity 0→1` + `translateY(10px)→none`, 380ms `cubic-bezier(0.2, 0.8, 0.2, 1)`) is the default "this just appeared" animation — `.card`, `.stat-tile`, `.pie-chart-wrap` (covers every chart shape, including the SVG line chart, since they all share that wrapper), `.bar-chart-row`, `.badge-card`, `input[type="search"]`, `.admin-topbar h1`, and on desktop commander.html's/player.html's open-by-default filter panel (`backwards` fill only, so it never overrides the panel's own fade-out afterwards; hidden by `body.is-loading` until the reveal, since its own `visibility: visible` would otherwise show through the hidden loading region). Reach for this one before inventing a new keyframe for "a card/row/tile just rendered".
- **Page-load reveal, all at once**: every public page's `body` starts with class `is-loading`; `body.is-loading * { animation-play-state: paused }` freezes every animated element (anything using `entrance-fade-up` or similar) at its first frame the instant it's inserted, however long before the page is actually "ready". `js/page-loading.js`'s `hidePageLoading()` removes `is-loading` at the same moment it fades out the splash overlay, so every element's entrance plays together, in sync, rather than each finishing invisibly off in the background the moment it happened to render. **Catch: an `animation` shorthand resets `animation-play-state` to running, so an entrance animation declared with a selector that outranks `body.is-loading *` (0,1,1) — an id, two or more classes, or a `:not(#id)` — is *not* paused: it plays and finishes unseen while the page loads. Each of those needs its own `body.is-loading <selector> { animation-play-state: paused }` in the list right after that rule** (there: the detail pages' filter panels, player.html's card, the list pages' search box). **Any new element given an entrance animation must also be added to the `@media (prefers-reduced-motion: reduce)` block right after the stagger `:nth-child` group in `styles.css` (the one listing `.card`, `.history-panel`, … `.badge-card`, `.bar-chart-row` — its `animation: none` is `!important` on purpose: most of those elements declare their animation later in the file, which would otherwise win on source order and keep animating for reduced-motion visitors) that sets `animation: none`** on this same list — otherwise a motion-reduced visitor never sees it at all (the animation is disabled, which for a *paused* animation means it stays stuck at its invisible first frame forever, not "instantly visible" as reduced-motion is supposed to mean). This exact gap is what caused detail-page titles to stay invisible through an entire page load for reduced-motion users before that specific animation was removed (see the "titles" guideline below).
- **Staggered cascade**: a fixed `:nth-child(2)`…`:nth-child(5)`, `:nth-child(n + 6)` selector group (45ms/90ms/135ms/180ms/225ms `animation-delay`, capped at 6 steps rather than queuing a long list one-by-one) is shared by every repeating grid/list of cards — `.stat-tile`, `.badge-card`. Add a new repeating item type to this *same* selector group rather than writing its own stagger rule. (A different stagger convention — inline `style="animation-delay: ${i * 60}ms"` set from JS — is used instead for `.pie-legend-item` and `.bar-chart-row` rows (`js/metagame-chart.js`), since those come from a dynamically-sized array with no natural CSS `:nth-child` cap; match whichever convention fits the situation, don't mix both on one element type.)
- **Popup/dropdown open**: `cs-menu-in` (custom-select) and `cd-popup-in` (custom-date) — both `opacity 0→1` + `translateY(-4px)→none`, 140ms `ease` — are the shared "small panel opening beneath a trigger" animation (`.matchups-dropdown` reuses `cs-menu-in` directly rather than defining its own). `nav-dropdown-item-in` (the admin's touch nav list) and `search-circle-in`/`-out` (mobile full-screen search, see below) are closer cousins of this same idea for their own, more specific shapes.
- **Commander pairings (commander.html + Comandanti)**: **X + Y is the same pair as Y + X**, whichever seat each was entered in. `commander.html?id=X` is the generic page — every entry with X as main **or** partner ("Tutti"); `&partner=<id>` only the games X played with that partner, `&partner=none` only alone. js/commander-detail.js loads X's entries once, derives the options (an entry's partner = its other commander, `partnerOf`), and `select(key)` redraws everything for one — stat tiles, Utilizzo, Giocatori, Storico partite (`renderSections(entries)`) — with "+ Y" in the title (`.commander-title-partner`, refitted) and Y's card (Scryfall, cached per partner) behind X's (`.detail-hero-card.has-partner`, `.commander-partner-figure`); the address follows with `history.replaceState` (no new history entry). Prefer matching an element's own animation's *shape*/vocabulary (expand vs. slide vs. fade) to whatever's already happening around it, not just reusing the nearest existing keyframe by default. - **Titles should generally *not* be animated, and should not be hidden/gated behind the page's loading state either.** `.page-heading h1` (the `<h1>` on every commander/player/event/league detail page) deliberately has **no** entrance animation, unlike `.admin-topbar h1` (which keeps `entrance-fade-up`, since admin tab headers are always static text, never swapped). The difference: a detail page's `<h1>` starts as a plain "Caricamento..." placeholder and gets overwritten in place once the entity's name loads — animating that swap, or hiding it until "ready" (both were tried and reverted this session), makes the transition itself feel like a deliberate, designed part of the page instead of what it actually is: a title that's simply there from the first frame and updates like any other text would. The name genuinely isn't known before that first fetch resolves, so a brief "Caricamento..." is an accepted, deliberate trade-off — not a bug to keep re-solving with cleverer CSS. ## Non-obvious gotchas (hit and fixed this session — avoid repeating)

**General rule, not just a gotcha — worth applying proactively, not only when something visibly breaks**: any popup/dropdown/tooltip (a select's own menu, a date picker, a search dropdown, a table-cell tooltip, a close button meant to float above everything) must reliably paint above ordinary static page content around it — chart cards, data tables, nav bars, whatever else happens to be a sibling or nearby ancestor. This site has hit the *same underlying failure* from several different specific causes now (gotchas #1, #2, #10, #11, #12, #13 below) — an `overflow: hidden` ancestor clipping it outright, a stacking context accidentally trapping its `z-index` below a later sibling, an animated `transform` hijacking a `position: fixed` element's containing block. When adding any new popup-like UI, don't just give it a z-index and assume it works — actively check: (a) does every ancestor between it and the page root allow `overflow: visible` at the moment it's shown (not necessarily always, e.g. during a collapse animation), and (b) does any ancestor's `animation`/`transition`/`transform`/`filter`/`perspective`/`view-transition-name` force an unintended stacking context that caps its `z-index` below whatever it needs to outrank.

1. **`overflow: hidden` on an element clips its own `::before`/`::after` too**, even ones meant to render outside its box (tooltips, dropdown shadows). If an element needs both truncation (`text-overflow: ellipsis`) *and* to host an absolutely-positioned popup/tooltip, put the truncation on an inner wrapper instead and keep the outer element unclipped.
2. **A scrolling container's `overflow-x: auto` forces `overflow-y` to also clip** (per the CSS overflow spec, whichever axis isn't explicitly set gets forced to `auto`/clipping too once the other is non-`visible`). A tooltip/popup anchored inside a horizontally-scrolling table (`.matchups-matrix-wrap`) cannot escape that clipping with CSS alone — it has to be a real element positioned via JS (`getBoundingClientRect`) and appended to `<body>`, outside the clipping ancestor. Use the shared `js/floating-tooltip.js` (`attachHoverTooltips(container, selector, textFor)` — the site's only tooltip: badges/banned icon/"Top 8" pill site-wide via `js/layout.js`, the Matchups headers and the Comandanti bar-chart labels; `fullTextIfTruncated` shows it only when a label is actually cut off; hover + keyboard focus; on touch, a tap on a badge inside a link card only shows its tooltip — `js/layout.js` cancels the link's click in the capture phase, mouse clicks still follow it).
3. **`mouseenter`/`mouseleave` don't bubble**, so event-delegation on a parent needs the capture phase (`addEventListener(type, fn, true)`). And if the hovered element has a child (e.g. a truncation `<span>` inside a `<th>`), capture-phase mouseenter/mouseleave fire *separately* for the child too as the cursor crosses that inner boundary — guard against re-triggering show/hide by tracking the currently-active target and checking `relatedTarget` on leave.
4. **`display: inline-flex` doesn't imply column direction.** A flex wrapper with two `width: 100%` children (e.g. a nav link + its submenu, in the mobile always-visible layout) needs an explicit `flex-direction: column` override, or the children sit side by side and the second one gets pushed off-screen — invisible, not just misaligned, if the ancestor also has `overflow-x: hidden`.
5. **Android's adaptive-icon system shrinks a non-`maskable` PWA icon defensively** (lots of padding) since it doesn't know how a launcher will crop it. A `purpose: "maskable"` icon variant with content filling ~70–80% of the canvas (this site uses 70%) against an opaque background fixes it — transparent backgrounds don't work for maskable icons, the OS crops the full square regardless.
6. **`beforeinstallprompt` is Chrome/Android-only** (and Edge / Samsung) — Safari/WebKit has never implemented it, on iPhone or iPad; the only install path on iOS is the manual Share → "Add to Home Screen". **The "Installa l'app" invitation** (`js/pwa-install.js`, since 2026-10-19): once per visit (a session), ~1.5s after the content is in (`body.is-loading` gone), sliding up — the first 3 visits every time, then at most once every 7 days, never again after 3 "Non ora" (cancelling the browser's own install window counts as one) or once installed (`appinstalled` / accepted) or already open as the app; state in localStorage `pwaInstall` / `pwaInstallAdmin` (`{shows, dismissals, lastShown, installed}`; the old one-shot `pwaInstallAsked` flag is removed on load). With `beforeinstallprompt`: a card (`.pwa-install-banner` — phones above the tab bar, computers bottom-right) whose "Installa" calls `prompt()`; iPhone / iPad: a bottom sheet (`.pwa-install-sheet`) with the Condividi → Aggiungi alla schermata Home steps; Android inside an app's own browser (Instagram, Facebook, WhatsApp…, UA sniffed): a sheet on opening it in Chrome and installing from the ⋮ menu; anything else: nothing.
7. Service worker (`sw.js`): **Scryfall's card images** (`cards.scryfall.io`, cache first, cache `scryfall-images-v1`, at most 300 — the oldest dropped; bump the version to empty it) — their addresses are versioned, so never stale; **the site's own files** network first, a copy as the offline fallback (`site-shell-v1`); **Supabase's data** (since 2026-10-19, `supabase-data-v1`, at most 400): REST GETs **stale-while-revalidate** — the last visit's copy answers at once, the network's replaces it behind (waiting briefly for the network first was tried 2026-10-26 and dropped: pages shown as soon as possible come first), keyed per account (the token's `sub`, "anon") and Accept / Prefer header; a changed body → `postMessage("data-updated")` → `js/data-updates.js` redraws the page **quietly** (since 2026-10-26 — before, a full in-place reload that flashed: splash, fade, animations again) if it's within 6s of arriving and untouched — `router.refresh({ keepScroll: true, quiet: true })`: a view transition whose update swaps `<main>`, mounts it and waits until it's whole (`whenDrawn`: splash gone, no `.sk` placeholder left outside it, the images in view decoded; ≤3s in all, `QUIET_MAX_WAIT`) while the browser keeps the old frame — the old screen's painted art and hero colour carried over first (`carryPaintedArt`: style / `data-url` / `is-loaded` / `has-hero-accent` of main, `.detail-hero-wrap`, `.profile-hero`, `.profile-hero-art`, `.pc-art`, so the painter skips the same art) —, then a 200ms cross-fade (`html.is-quiet-refresh`: no other transition names, every animation **and transition** jumped to its end — **except the phones' hero parallax** (`.profile-hero.is-parallax`, its art and content: scroll-driven, and its "end" is the hero pushed down by half and blurred — every quiet redraw on a hero page showed that for a moment, the "white top", until 2026-10-28) —, no count-up, `mix-blend-mode: plus-lighter` on the root's old/new — our `animation` drops the browser's own blend, and without it the cross-fade dipped to the bare background: a white flash over a dark hero (fixed 2026-10-28, same for the theme switch); Mentioned in privacy.html's "Cookie".
8. **A generic dark-mode override can win on specificity over a more specific context rule that resets a background to transparent**, even when that rule is more semantically "specific." The generic dark-mode "give this a faint card background" rules (`styles.css`, the big `:root[data-theme="dark"] .card, .stat-tile, .pie-chart-wrap, ...` list) are 3 classes; a narrower "this one shouldn't have its own background, it's nested inside another card" rule like `.dashboard-card-commanders .pie-chart-wrap { background: none; }` is usually only 2 — the generic rule wins regardless of source order, silently reintroducing a visible background the narrower rule was trying to remove. Hit **three separate times** this session with this exact shape (`html.nav-mobile .site-nav`, `admin/admin.css`'s `.admin-tabs`, and `.dashboard-card-commanders .pie-chart-wrap`) — worth checking for this pattern by default whenever a "make this transparent/none in context X" rule doesn't seem to be working in dark mode specifically. Fix is always the same: a compound selector combining `:root[data-theme="dark"]` (or `html[data-theme="dark"]`) with the narrower context class(es) in one selector, placed near the other dark-mode overrides, not just relying on cascade order.
9. **Wrapping already-class-gated CSS in a redundant `@media` condition means BOTH have to independently match, and they can disagree.** The mobile-pill CSS was originally inside `@media (max-width: 640px) and (pointer: coarse) and (hover: none) { html.nav-mobile .site-nav { ... } }` — belt-and-suspenders with the JS-set class, in theory. In practice, some browsers (Samsung Internet) misreport `pointer`/`hover`, so the `@media` condition silently failed to match even when `html.nav-mobile` was correctly set by JS — the styling just never applied, with no error, nothing to debug from the DOM (the class was right there). Fixed by dropping the `@media` wrapper entirely and trusting the JS-set class as the single source of truth, rather than trying to patch the media query further.
10. **`perspective` and any CSS `animation`/`transition` that animates `transform` both create a stacking context on whatever element they're set on**, for as long as `animation-fill-mode` holds it there (not just while actively animating). A sibling element positioned to overlap that one (e.g. the commander card's flip button sitting over the card image) can become unclickable even with `pointer-events: none` on its own icon, because the *ancestor* now stacks the whole overlapping region above the sibling. Fix: keep `perspective`/animated-`transform` rules on a dedicated inner wrapper, never on the same element an interactive sibling is positioned against — see the commander card's `.commander-card-perspective` split from `.commander-card-figure` above.
11. **A non-`none` `view-transition-name` forces its element into its own stacking context**, same as `perspective`/animated-`transform` above (gotcha #10) but easy to miss since nothing about the property *looks* stacking-related. `.site-header` has `view-transition-name: site-header` (so cross-page navigations treat it as one continuous element) but no explicit `z-index` — meaning that whole forced stacking context only ranked as `z-index: 0` among its siblings, so `.site-nav` right below it (`position: sticky; z-index: 20`) painted *over* it regardless of any `z-index` set on elements *inside* the header (the site-wide search dropdown's own `z-index: 60` couldn't escape it — a descendant's `z-index` only ever competes within its own stacking context, never past it). Fixed by giving `.site-header` itself an explicit `position: relative; z-index: 25` so the whole header, dropdown included, outranks the nav bar. Worth checking for on any other element that sets `view-transition-name` and later turns out to have positioned children needing to float above a later sibling.
12. **An animated (or merely non-`none`) `transform` on an ancestor becomes the containing block for a `position: fixed` descendant** — that descendant then positions itself relative to the *transformed ancestor's* box, not the viewport, defeating the entire point of `fixed`. Hit in `js/site-search.js`'s mobile search overlay: the close button is `position: fixed`, pinned to the exact px spot/size the trigger button occupies (via `getBoundingClientRect()`-derived CSS custom properties), but it originally lived inside `.site-search-bar`, which the entrance animation (`search-content-in`) applies `transform: scale(...)` to — mid-animation, the "fixed" button would have scaled and moved right along with the bar instead of staying stationary at the trigger's real position. Fixed by animating `.site-search-field` alone instead of the whole `.site-search-bar`, since the field doesn't need to stay put the way the close button does. Whenever a `position: fixed` element needs to stay genuinely pinned to the viewport, check every ancestor up to (but not including) the one it's meant to escape for an animated/set `transform` (or `filter`/`perspective`/`will-change` naming one of those) — not just whether the *element itself* has one.
13. **A `grid-template-rows: 0fr/1fr` collapse animation needs `overflow: hidden` on the collapsing grid item to work at all** (same reasoning as gotcha #1's clipping issue, but here the clipping is *load-bearing*, not incidental) — without it, the item's default `min-height: auto` keeps it rendered at full content height regardless of the row track's own animated size. That same `overflow: hidden` then clips any select/date popup that opens *inside* it, though, since those position themselves relative to their own field, a descendant of the clipping box — the popup gets cut off right at the (small, collapsed-content-height) box's own edge, which reads as "cut off by whatever page content happens to sit right above/below the filter box" rather than an overflow bug. Hit in `.filter-panel-clip` (Comandanti/Giocatori/Archetipi's collapsible filter box, `js/filter-toggle.js`). Fixed by toggling the clipping itself, not just relying on `.cs-wrap.is-open`'s own `z-index: 30` (that only helps once a popup can actually escape its containing box, which `overflow: hidden` prevents outright, no z-index fixes that) — `.filter-panel-clip.is-open` switches to `overflow: visible` once the expand transition's own `transitionend` fires (confirmed still expanding, not right when the click happens, or a popup opened mid-animation would already escape while the row is still visually only partway open), and switches back to `hidden` immediately on collapse, before that animation starts, so the shrink itself still clips normally.

- Comandanti and Giocatori lists: after the winrate (and Comandanti's metashare, the same rule — since 2026-10-19) a trend arrow in a small disc tinted in its colour (since 2026-10-21; it was ▲ / ▼ / =) — **↗ (green) / ↘ (red) / → (grey)** — since 2026-10-21 two rules: **Winrate** — now vs. without the commander's / player's **own** latest event within the filters' scope (`latestPresence` in js/history-list.js; events outside the filters never count); → when that was their only event in scope. **Metashare** (its decks ÷ every deck in scope) — **global**: now vs. without the latest event in scope, whoever played in it — ↘ when it had a smaller slice of that event than its average or wasn't in it, ↗ when bigger (from 0% when it was its first); → with a single event in scope. Both computed by subtracting that one event's own numbers (results add up event by event; js/commanders-page.js, js/players-page.js), compared at the shown precision (one decimal, `winrateTrendHtml`); nothing for a "—" winrate. (A per-commander Metashare was tried and dropped: its own last event always holds it, so it nearly always read ↗.) Hangs outside the number's box (`.wr-trend`, absolute) so the number stays centred in its column. Since 2026-10-19.

## Winrate sample threshold (Comandanti)

- Since 2026-10-20 (js/commanders-page.js `MIN_PLAYED_RATIO` = 0.3): a commander's winrate counts only with at least 30% of the matches of the most played commander in the same scope (filters included — relative, so it scales from one event to the whole history). Below it: left out of the Winrate chart, sorted after the others when sorting by winrate, its winrate greyed in the list (`.wr-few`, "Pochi dati" on hover). The chart groups by primary commander, the list by pairing: each computes its own threshold.
